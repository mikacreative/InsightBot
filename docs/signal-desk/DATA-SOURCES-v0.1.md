## 0. 结论摘要

1. **千瓜与 JustOneAPI 不是替代关系，是互补关系。** 千瓜的独有价值在**它自研的结构化指标**（品牌 SOV、达人金字塔、类目漏斗、榜单），这些是任何"抓公开页面"的供应商都买不到的；JustOneAPI 的独有价值在**完整笔记正文（经 `get-note-detail`）**与**蒲公英达人投放数据**，这些是千瓜接口面里根本不提供的。
2. **正文可达性的结论需要二次修正。** ——① 对千瓜：正文**不可达**（三重取证，成立）。② 对 JustOneAPI：**`get-note-detail/v1｜v6` 可达完整正文**，但 **`search-note` 接口返回的 `desc` 是截断摘要（≤60 字符），不是正文**。2026-10-11 本机 MCP 端到端实测（v2 20 条 + v4 17 条样本）推翻了"搜索即含正文"的推断——**取正文须 N+1 次 detail 调用**。详见 `JUSTONEAPI-ASSETS.md` §2.5。
3. **窄额度指标应当排除出设计，但不是因为"指标没价值"，而是因为"绑定错源"。** 评论搜索在千瓜是 15 次／月的奢侈品，在 JustOneAPI 是按次计费的普通商品——需求应路由到后者，而不是从方法论里删掉需求。
4. **成本模式的根本差异是固定成本 vs 变动成本。** 千瓜按席位收年费、额度按月重置；JustOneAPI 按成功调用计费、余额不过期。对"每期 0—3 条精选"这种低频高价值产品，席位制是结构性浪费。
5. **建议采用双源分工**：千瓜承担结构／对照层（L3／L4／T），JustOneAPI 承担原文／人群／跨平台层（L1 正文／L2 深度）。
6. **✅ 单价已从"推测"升级为"官方确证"（2026-10-11 本版新增）。** 拿到控制台**全量价目表**（296 端点 × 35 平台，¥0.05—¥1.50），据此**更正正文单价为 ¥0.15／次**（此前记为"≤¥0.10／未观测到扣费"）。⚠️ **成本模型整体上调约 50%**（§6.2）。误判根因：**计费异步结算**——单笔延迟入账，差值恰好伪装成"该端点免费"。
7. **✅ 千瓜给不出正文，已从"endpoint 级确认"升级为"实测确证"。** `note.search_by_url` 实测返回 **40 个字段，无任何内容字段**（`Title` 17 字符、`Tag` 空、`VerifyContent` 不存在）→ **千瓜在本项目里最高只能到摘要级**，`note_body` 唯一来源是 JustOneAPI detail 接口（§1.3）。
8. **✅ 证据等级已收敛为单一真源。** `insightbot/signal_desk/grades.py` 承载八等级 + rank + `summary_only` + alias 归一，**未知等级 fail-closed**；`qiangua_body`（幻影等级）降为 `note_segment`。**"两套词表并存"状态终结。**

> 详见 `JUSTONEAPI-ASSETS.md`；体检用 `scripts/justone_mcp_probe.py`。

### 2.1 服务形态

| 项 | 内容 |
| --- | --- |
| 接口形式 | REST，`https://api.justoneapi.com`；中国大陆可用 `prod-cn` 节点（`http://47.117.133.51:30015`） |
| 鉴权 | URL 参数 `?token=<access_token>`，控制台管理 |
| 计费 | **按成功调用计费**（返回体 `code=0` 才计费）；余额**不过期**；注册赠免费测试次数 |
| 配额 | 无通用速率限制；管理员可设"用户×接口"每日成功请求限额，超限返回 `303`／HTTP 429 且**不计费** |
| 官方 SDK | `pip install justoneapi`（Python，同步／异步） |
| **来源** | 使用指南 `https://docs.justoneapi.com/zh/usage`（公开）；价目 `https://dashboard.justoneapi.com/zh/dashboard/pricing`（**需登录**，唯一官方价目来源） |

**计费码与限额的两条硬规则**（2026-10-11 对官方使用指南逐条核对，见 `JUSTONEAPI-ASSETS.md` §2.9）：

1. **只有 `code=0` 计费。** `100`（Token 失效）／`301`（采集失败）／`302`（超速率）／`303`（超每日配额）／`400`／`500`／`600`／`601`（余额不足）／`602`（TOKEN 限额超限）**全部不计费**。已转录为 `costcontrol.BILLING_CODES`，`settle(code=...)` 据此结算。
2. **令牌限额不是资金划拨。** 官方原句："多个 TOKEN 仍共享同一个账户余额。"→ `budgetAmount` 只约束绑定该令牌的通路，**账本才是防双花的正确位置**。
3. **本地门禁已于 2026-10-11 晚接线。** 付费正文读取（`research_v2.enrich`）逐次 `require()` → `settle(code=...)`；信封只从 `SIGNAL_DESK_SPEND_LIMIT_CNY` 声明，**未声明即不花钱**（退回免费片段并把原因写进 limitations）。**"有 token" 与 "被允许花钱" 正式分开。** ⚠️ MCP 直调通路不走本账本。

> ⚠️ **本节的"配额"规则尚未在代码里建模**：`costcontrol.Envelope` 只表达货币上限，不表达"每日成功次数"。后果是方案**可能通过金额校验、却在调用时被上游以 `303` 拒掉**。是否把次数也纳入信封，属待决的产品判断（`JUSTONEAPI-ASSETS.md` §2.9 C）。
| 官方 MCP | 远程 HTTP `https://mcp.justoneapi.com/mcp`（Bearer token）或本地 `npx justoneapi-mcp` |
| 调用方式 | 每接口单次请求、单页返回，**不自动翻页**（示例明确说明） |

**关键架构含义**：JustOneAPI 是纯 API token 模式，**没有席位概念、没有前端流程计量**。这与千瓜"账号＋席位＋前端扣费"的形态形成对比——前者天然适配自动化与 Mac mini 常驻执行，后者天然要求人工在 UI 里操作。

## 5. 窄额度指标的处置规则

### 5.1 纳入设计的门槛

一个能力要进**证据配方（主路径）**，必须通过额度门槛检验：

```
可用品牌数 = 月额度 ÷ (单品牌单期调用量 × 每月期次)
```

按人工量级（单品牌：Scan 2—3 次／期、Probe 5—10 次／事件），单品牌月用量约 **30—50 次**。取 40 次为基准：

| 档位 | 月额度 | 可支撑品牌数 | 处置 |
| --- | --- | --- | --- |
| 宽 | ≥2400 | ≥60 | **主路径**：可作证据配方的默认能力 |
| 中 | 200—900 | 5—22 | **按预算使用**：用于结构／定向研究，需在期次规划里声明 |
| 窄 | ≤50 | **<2** | **不进设计**：不作为任何配方的必需能力 |

### 5.2 按此规则被排除的能力（千瓜侧）

| 能力 | 额度 | 被判排除的理由 |
| --- | --- | --- |
| 评论搜索 | 15／月 | 支撑品牌数 <1；本期已归零 |
| 笔记内容解析 | 20／月 | 支撑品牌数 <1 |
| 店铺搜索 | 10／月 | 支撑品牌数 <1 |
| 品牌对比 | 50／月 | 边界值：仅可作为季度 Frame 的单次调用，不得作为周度配方的常规步骤 |
| 直播录屏、评论相关笔记分析报告 | 0 | 套餐不含 |

### 5.3 但"排除"指的是排除**千瓜这个源**，不是排除**这个需求**

这是本节最重要的区分：

- **评论需求**（用户自述语言、异议、复购信号）在方法论里仍然成立，且属于 L1 中信息密度最高的部分。
- 它在千瓜被判排除，唯一原因是**额度绑定过窄**。
- 在 JustOneAPI，评论是**按次计费的普通调用**，无月度边界。
- 因此正确处置是：**把评论需求从"千瓜配方"改路由到"JustOneAPI 配方"**，而不是降低方法论的证据等级。

> 一句话规则：**能力取舍看获取成本，不看指标价值。** 一个指标"值不值得要"由决策任务决定；"从哪里取"由额度结构决定。

## 6. 成本核算

### 6.1 千瓜：固定成本（席位制）

| 项 | 数字 |
| --- | --- |
| 年费 | ¥60,000 |
| 席位 | 15 |
| **单席位成本** | **¥4,000／年 ＝ ¥333／月** |
| 额度重置 | 按月（按购买日滚动） |
| 额度属性 | 逐功能独立；**实测为账号／token 级**（`GetUserOperationCountV3`） |

**两个必须核实的问题**：

1. **额度是"账号级"还是"席位级"？** 实测的 `GetUserOperationCountV3` 是账号级读数。若额度账号级共享，则**加席位不增加额度**——15 席位只解决"多人可登录"，不解决"额度不够"。
2. **15 个席位实际有多少活跃使用？** 若日常只有 1—3 人操作产品，则其余席位是纯闲置成本。

### 6.2 JustOneAPI：变动成本（按次）

| 项 | 内容 |
| --- | --- |
| 计费单位 | **每次成功调用**（`code=0`），失败调用不计费 |
| 余额有效期 | **不过期**（无时间压力，天然适配低频使用） |
| 单价（**2026-10-11 官方价目表确证**） | `search-note/v2` **¥0.15／次**；**已切用的 `search-note/v4` ¥0.20／次**；`get-note-detail/v1｜v6` **¥0.15／次**；`get-note-comment/v2` **¥0.15／次**。全表 296 端点 × 35 平台，区间 ¥0.05—¥1.50。⚠️ **本版更正**：detail 此前记为"未观测到扣费（≤¥0.10）"，实为 **¥0.15**（与 v2 同价） |

**单品牌年调用量估算**（人工量级，含翻页与详情展开）：

| 模式 | 每期调用 | 期次／月 | 月小计 |
| --- | --- | --- | --- |
| Scan（速读） | 1—2 | 4 | 4—8 |
| Probe（定向） | 5—10 | 2 次事件 | 10—20 |
| Frame（结构） | 20—30 | 1 | 20—30 |
| **合计** | | | **约 35—55 → 取 50 次／月** |

年用量 ≈ **600 次／品牌／年**。

> **v0.2.6 口径修正**：上表 Scan 的"1—2 次"是**只算检索**时的估算。配方与产出核对后，Scan 一轮为 **2 次检索 ＋ 1 条正文 = 3 次**（依据：§3 要求计划至少含一条挑战查询；§2.2 禁止把 ≤60 字符摘要当语言复用，而 §4 承诺 Scan 产出"在用的词"）。因此 Scan 一项由 4—8 次／月升至 **12 次／月**（4 期 × 3），**该行口径已失效，勿再引用**。年用量仍取 **600 次／品牌**量级，但成本口径应改为**按模式分档**（§4.1／§2.8 F），而不是单页均价。详见 `JUSTONEAPI-ASSETS.md` §2.8 F。

**单品牌年成本（基于**官方确证**单价重算，2026-10-11）**：

| 组合 | 单页成本 | 年成本／品牌 | ¥60,000 可支撑品牌数 |
| --- | --- | --- | --- |
| 纯检索（只取 60 字符摘要） | ¥0.20 | **¥120** | 500 |
| 检索 + 每页取 10 条正文 | ¥0.20 + 10×**¥0.15** = **¥1.70** | **¥1,020** | 58 |
| 检索 + 每页取全部 17 条正文 | ¥0.20 + 17×**¥0.15** = **¥2.75** | **¥1,650** | 36 |

> **关键读数**：取正文是成本主项，占单页成本的 **88—93%**（修正前为 83—91%——**基数上调后正文占比更高**）。
> **决策含义**：正文**不应全量取**——只在"本期精选 0—3 条"的终选阶段对候选取正文，恰好与 PDD §1「不以数据量替代客户价值」同向。若按此口径（每期 3 条正文 + 5 页检索），单品牌月成本 ≈ **¥1.0 + ¥0.45 ≈ ¥1.45**，年成本 ≈ **¥18**。

### 6.3 关键对比：固定成本模式对低频产品不经济

千瓜单席位月额度（仅计宽额度档）：

```
热搜词 6000 + 笔记分析 4500 + 跳转原文 4500 + 笔记搜索 4000 + 达人搜索 2400 + 关键词搜索 800
≈ 22,200 次／月
```

产品实际用量（按 PDD §7.2「本期精选 0—3 条」，人工量级）：

```
3 个品牌 × 50 次／月 = 150 次／月
```

**利用率 ≈ 0.7%**（即便只算笔记搜索 4000／月，利用率也仅 3.75%）。

这不是"买贵了"，而是**成本结构与产品形态错配**：席位制要求你为"能调用的次数"付费，而产品的价值主张恰恰是"不需要那么多次数就能做出判断"（PDD §1 明确不以数据量替代客户价值）。

### 6.4 双源方案成本

| 方案 | 年成本 | 说明 |
| --- | --- | --- |
| 仅千瓜 15 席位 | ¥60,000 | 得到结构层 + 大量闲置额度；**但拿不到正文** |
| 千瓜 + JustOneAPI | ¥60,000 + ≈¥180×N | N = 品牌数；@¥0.30／次，20 品牌 ≈ ¥3,600 |
| 仅 JustOneAPI | ≈¥180×N | 便宜，**但拿不到 SOV／金字塔／榜单** |

**结论**：JustOneAPI 的增量成本相对千瓜是小项（@20 品牌约 6%），但它补上的是**千瓜结构上缺失的能力**（正文、评论原文、跨平台）。真正值得议价的空间在**千瓜席位数量**，而非供应商替换。

### 6.5 降本路径（按优先级）

1. **核实席位真实需求**：若活跃席位 ≤3，与千瓜协商降至实际席位档 —— 这是单笔最大节省项。
2. **把可替代能力迁到 JustOneAPI**：笔记搜索、笔记分析、达人详情、评论——这些千瓜侧额度紧张或能力不足，迁移后千瓜额度专供结构层。
3. **用免费额度先验证**：JustOneAPI 注册赠次，可零成本跑通 ① 检索接线 ② 正文可达的端到端验证（符合"先建后停、可零成本回滚"的推进习惯）。
4. **余额不过期**：JustOneAPI 无月度归零压力，可按项目节奏充值，不产生沉没成本。

## 7. 建议的采集架构

```
证据层       主源              备源            降级
─────────────────────────────────────────────────────────────
L1 内容      千瓜（宽额度）      JustOneAPI       只记现象
  正文       JustOneAPI        （人工打开原文）   标注 title_only
  评论       JustOneAPI        千瓜（15／月）    本期跳过
L2 人群      千瓜（类目画像）    JustOneAPI       标注口径
  粉丝趋势   JustOneAPI         —                本期跳过
L3 结构      千瓜（独占）        —                标注"结构层缺席"
L4 商业      千瓜（平台内榜）    JustOneAPI（跨平台）  标注渠道口径
T  时间      千瓜（趋势序列）    自建同口径重采样   标注"仅样本内"
```

> **取数链路提示（2026-10-11 端到端实测后新增）**：
> - **正文**：搜索层（v2／v4）`desc` 一律截断 ≤60 字符，**只能当"提及／话题"级证据**；完整正文须对候选笔记调 `get-note-detail/v1｜v6`（N+1，**¥0.15／条**）→ 因此正文取样应**后置于终选**（每期 0—3 条），而非全量展开（全量取 = ¥2.75／页，是纯检索 ¥0.20 的 **13.75 倍**）。
> - **评论**：`get-note-detail` 的顶层 `comment_list` 实测为空，**评论必须单独调 `get-note-comment/v2`**；`search-note` 也不返回评论。这意味着千瓜"评论搜索 15／月"的缺口不能靠搜索接口顺手补上，需独立配额与独立成本。
> - **URL**：搜索返回的 `url` 恒为空，但 `explore/<id>` 裸 URL 实测 200 可访问，归一化逻辑无需签名参数。

**三条设计约束**：

1. **供应商可替换性写进配方**：每个证据配方声明「主源／备源／降级」，避免把某个供应商的临时故障升级成产品故障。
2. **来源必须随证据落库**：`note_meta` 等分级需带 `source` 字段（`qiangua` / `justoneapi` / `manual`），否则跨源拼接后无法复核。
3. **额度与预算前置于执行**：调度器在期次规划阶段读取两源可用量（千瓜 `user.quota` + JustOneAPI 余额），再决定采样规模。
