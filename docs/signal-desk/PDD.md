## 1. 本轮决策与产品价值

本轮依据 Mika 2026-10-07 的明确要求，以及 Sun Life RedNote v11 的产品售卖构想修订：

- 产品保持独立，可应用于多个品牌。产品方法、工具和质量规则可复用；品牌目标、研究任务、证据和决策记录分别管理。
- 以交互式 Agent 建立任务，以策略核心组织研究，以 editorial pipeline 保证证据和交付质量。
- 数据源按**能力**分工，不设单一主源：**千瓜**承担**检索**与**结构／对照层**（品牌 SOV、达人金字塔）及**关键词时间序列**；**JustOneAPI** 承担**笔记正文与评论原文**——这正是千瓜做不到的部分（`note.search_by_url` 实测仅返回 40 个字段、不含任何内容字段）。网站搜索与 RSS 补充外部语境。保留旧运行的可读性，不删除已有凭证、适配代码或记录。
- 优先完成本机开发、真实数据测试与业务验收，再决定是否更新 Mac mini。此前远端部署不构成本轮发布。

产品帮助营销团队回答：当前该关注什么问题，有什么证据支持或挑战判断，哪些理解值得纳入讨论，以及新证据如何修正判断。品牌定向决定观察坐标，不预设结论。独立性指方法与证据不迎合预设答案，不宣称无偏见或具有第三方认证。

首期按内部团队使用、人工交付的服务产品设计。产品独立不要求立即拆分仓库；同仓模块化与独立产品体验可以并存。不以数据量、生成篇数或自动化程度替代客户价值。

## 2. 产品结构与品牌分区

信息架构：`产品首页 → 品牌工作区 → 议题／任务 → 研究运行 → 精选判断与交付 → 跨期回看`。

| 层级 | 核心对象与操作 | 边界 |
| --- | --- | --- |
| 产品首页 | 新建／选择品牌、查看有权限品牌的待办与运行状态 | 不默认聚合展示客户原文、策略或凭证 |
| 品牌工作区 | 品牌资料、目标、人群假设、竞争范围、语言与地区、成员、来源设置、服务方案 | 持续显示当前品牌；切换品牌清空上一品牌临时对话上下文 |
| 持续议题 | 长期问题、已知判断、反例、未解决问题、历次结论 | 同一议题可有多次任务，不靠重复检索词识别关联 |
| 研究任务 | 问题、对话、可编辑方案、节点流程、执行时间与历次结果 | 可手动运行或按确认的时间自动运行，每次结果分别审阅；也可关联议题 |
| 运行与交付 | 执行记录、证据、精选卡片、讨论参考、交付期次、审核版本 | 单次运行不等于一期交付；一期可汇总多次运行 |

品牌资料分为经确认事实、客户给定假设、团队研究判断与未确认材料，均记录来源和版本。研究计划保存所用品牌资料快照；资料变更不静默改写历史结论。

所有任务、证据引用、会话、checkpoint、缓存、反馈和交付必须绑定 brand_id；运行同时绑定 task_id、run_id。服务端按成员权限检查读写，不能只靠前端下拉菜单或文件路径。品牌管理员配置成员与范围，研究员创建任务，审核员批准交付；同一人可以兼任。角色如何映射既有 admin/editor 在实现时迁移，不以现有共享工作区冒充隔离完成。

跨品牌复用仅限通用研究模板、公共方法和经授权资料。客户材料、结论及私有反馈不能自动成为其他品牌的上下文。隔离验收通过前不向不同客户开放账号。

## 3. 交互式任务建立

员工从营销问题或项目描述任务，例如“我们的商品卖点与用户实际比较产品的方式是否一致？”或“小红书运营反馈一般，哪些现象值得进一步理解？”品牌背景不自动生成研究方向；生活话题仅在任务需要时作为观察材料。Agent 先确认决策用途，再补足会改变检索和判断的关键缺口；不要求员工填写完整技术表单，也不无限追问。

建议交互：

1. 选择品牌和已有议题，或新建任务；加载该品牌已确认资料。
2. Agent 提炼目标、使用场景、待验证假设，并区分用户指定条件和系统建议。
3. 提议人群／场景、主题、品牌与竞品、地区、时间窗、排除项、来源组合及深度；深度对应三种研究规模——速读（快速看清议题）、定向（验证一个判断）、结构（看清所处位置），并在方案里写明本轮采用的是哪一种。
4. 对话给出简短方案；任务详情用节点流程展示研究问题、来源、核对与精选、按需补读和人工审阅。点击节点查看方法与必要的数据口径，手动设置按需展开。
5. 用户点击“开始研究”确认当前方案，或先检查时间设置再启用自动执行。确认冻结 plan_version；范围内有限补证共享已确认额度。方案改变后，自动执行暂停，待检查新版本后重新启用。
6. 同一任务保留对话、方案版本与执行记录，先显示执行反馈，再呈现人工审核稿。区分“仍在采集”“证据不足”“无新信号”和“调用失败”。

任务目标采用可组合模板：品牌与竞争、平台运营、商品与卖点、人群与使用场景、内容与传播、达人方向、数据变化。达人方向既可作为独立任务，也可作为相关任务的研究路径。模板是研究起点，不能把所有任务套进同一个热点摘要。高级配置可展开，凭证与供应商接口参数只向管理员提供。

> **命名注（2026-10-12 一致性复核）**：这七类在代码 `METHODS` 中的规范名是 `brand_competition`／`platform`／`product`／`audience`／**`content`（规范名「内容与沟通」）**／`creator`／`data_change`。本文此处写的"**内容与传播**"与 §4.1 表头的"**内容方向**"**指的是同一类**。⚠️ 代码别名表收录了"内容方向"，但**未收录"内容与传播"**——未收录时会落到默认任务 `content`，**恰好命中，属巧合对齐而非设计**。建议后续统一到规范名「内容与沟通」，或把"内容与传播"补进别名表（本轮未改代码）。

## 4. Intelligence 策略核心

策略核心是可解释、可版本化的研究决策方法，包含问题拆解、信号选择、来源路由、比较设计和编辑取舍；不是单一综合分数，也不是让大模型凭经验写洞察。

### 4.1 研究任务与信号路径

| 决策任务 | 首选信号与来源 | 判断路径 | 快速反馈与使用边界 |
| --- | --- | --- | --- |
| 内容方向 | 千瓜关键词笔记、评论、内容表达；网站原始研究与权威解释 | 问题／场景归类 → 已有解释与缺口 → 品牌能提供的内容价值 | 内容角度、证据缺口、可测试选题；高互动不等于普遍需求 |
| 平台运营 | 千瓜内容与互动样本、平台官方说明、用户导入运营指标 | 明确运营困惑 → 区分内容样本与后台指标 → 对照不同反馈 | 运营观察与需核验假设；没有后台数据不诊断算法或绩效因果 |
| 商品与卖点 | 品牌确认的产品事实、使用评价、替代选择与表达 | 品牌利益表达 → 用户理解与比较方式 → 识别差异与反例 | 卖点理解参考；不自动制定商品、价格或渠道方案 |
| 人群与场景 | 社交自述、提问、达人粉丝画像；外部研究 | 场景与障碍 → 不同经验 → 人群假设与验证方案 | 场景图、人群假设；作者和粉丝不能据此判定财富或购买意愿 |
| 达人方向 | 相关笔记作者、近期内容、合作记录及可用粉丝信息 | 议题匹配 → 表达角色 → 商业内容与证据检查 | 表达角色观察、候选线索与需人工核验项；样本作者聚合不是全市场排名 |
| 品牌／竞品 | 千瓜品牌趋势、话题、内容与合作达人；品牌官方网站 | 同窗同口径比较 → 表达差异 → 可探索空间 | 竞争观察与假设；无数据不能解释为没有布局 |
| 数据变化 | 可比较时间窗的千瓜指标、内容构成；用户导入运营反馈 | 检查口径与覆盖 → 拆解变化 → 提出解释与验证动作 | 异常说明、候选原因、下一步检查；相关性不等于因果 |

> **来源注（2026-10-12 修订）**：本表"首选信号与来源"列的是**谁能找到该信号**——检索命中与结构指标由千瓜提供（品牌 SOV／达人金字塔／关键词趋势属结构层与时间轴）。凡涉及**笔记正文、评论原文**的部分，**正文与评论由 JustOneAPI 承担**：千瓜的内容能力止于摘要／指标级（见 §5）。

产品只指出与内容、词组或投放讨论有关的信号，不自动给投放调整方案。即使接入广告后台，预算配置、KPI更改和策略取舍仍属于另外的人工作业，不因数据增加就自动扩大产品职责。搜索问题、关键词相关内容、搜索量和搜索广告份额分别命名，不能互相替代。

### 4.2 每项研究的共同步骤

`决策问题 → 可验证子问题 → 信号与比较设计 → 证据采集 → 主题及不同解释 → 品牌相关性 → 精选判断或补证 → 反馈更新`。

- 同时设计定向查询与挑战假设的查询。查询词、排除条件、排序和窗口必须保存。
- 比较需声明比较对象、时间窗、口径和覆盖。不以关键词自身命中的样本作为该议题在总体中的占比。
- 证据独立性按原始来源判断；同一报道在 RSS、搜索和社交转载中出现，只算同源传播，不能作为三份交叉验证。
- 判断依据包括相关性、证据质量、新信息、不同解释、参考价值；分别说明，不输出未经校准的“洞察可信度87%”。
- 每项主张关联支持证据、挑战证据、限制、推理理由和下一步验证。人群身份、规模趋势、因果与财务结论需更强依据。
- 新证据可以维持、修正、推翻或暂时搁置旧判断；保留版本与理由，不覆盖历史。

### 4.3 策略核心如何验证

0.2.1 提供七类营销任务的规划模板。采集能力以 §5 的分工为准：内容样本与评论原文、品牌级结构指标（品牌 SOV／达人金字塔）及关键词时间序列**已接入**；**类目级指标与广告后台未接入**。模板扩展不会自动接入新来源。必须披露数据能力边界，不能把样本比较写成全量运营诊断。为每种模板选择代表任务及证据不足样例，由策略人员检查：是否选对信号、是否遗漏反例、结论是否越界、参考意义是否具体且未越过证据。保存方法版本与人工修改理由。验收指标包括无依据主张数、实质修改率、精选判断的可追溯比例、审核耗时和单期成本；先测基线，再定阈值，不虚构准确率。

## 5. 来源策略与采集范围

| 来源 | 本轮角色 | 必须披露的限制 |
| --- | --- | --- |
| 千瓜 | 社交信号的**检索与结构层主源**：关键词、笔记与评论的**检索命中**，以及按任务选用的品牌／达人**结构指标**（品牌 SOV、达人金字塔、关键词趋势）| 依赖真实账号权限、接口字段、分页与覆盖；**内容能力止于摘要／指标级，给不出笔记正文**（正文与评论原文见 JustOneAPI）；能力目录存在不等于已接入产品或本次授权可用 |
| 网站搜索 | 有目的地补证、追溯原始研究、官方信息及不同解释 | 搜索摘要不是正文；记录检索时间、网页发布日期、原始链接和访问状态 |
| RSS | 在已配置的媒体／研究／机构来源中持续发现外部语境 | RSS是发现入口；摘要或转载需追溯原文，失败不能当成没有新信息 |
| 人工材料 | 品牌事实、已确认 Brief、运营表现和审核反馈 | 来源、权限、时间和确认状态明确，不混入独立外部证据 |
| JustOneAPI | **笔记正文与评论原文的唯一来源**（搜索接口 `desc` 恒为 ≤60 字符截断摘要，不构成正文）| 按**次**计费，逐次走 `costcontrol` 费控门禁；正文按"终选后按需取"（N+1 次 detail 调用，非检索时全量取）；未声明花费信封即不调用付费读取器；按业务码结算，仅成功码计费 |

千瓜接入参考本地 qiangua-insights 的 capability 契约：`content.search_notes`、`keyword.notes`、`content.comment_search`、`note.search_by_url` 等。品牌、达人和趋势接口按任务逐步启用。先做低成本只读鉴权和目标接口验证，不以浏览器登录状态作为授权依据。**能力存在不等于能拿到内容**：上述接口实测只回摘要／指标级字段，笔记正文须另经 JustOneAPI 的 detail 接口取得（见本节来源表）。

网站搜索适配器的提供商与额度待技术验证，不默认调用交互聊天工具作为生产后端。RSS配置来源白名单、抓取频率和上限。外部来源不可用时允许输出受限研究，但要明确缺失语境，不宣称多源核验完成。

每次计划约束查询数、页数、样本数、正文读取数、模型调用、超时与补证轮次。数量均为上限，不是最低产量。现有“1次搜索、20条样本、1次AI”只是旧版运行限额，不作为所有研究方法的固定设计。

## 6. Agent、策略核心与 Editorial Pipeline

| 层 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 交互 Agent | 澄清任务、读取品牌上下文、提出和解释计划、反馈状态 | 自行扩大权限、预算或替客户批准交付 |
| 策略核心 | 研究模板、信号路由、比较与反例设计、证据到精选判断的解释链 | 用热度或机械打分替代研究判断 |
| Editorial pipeline | 去重、证据与主张匹配、初筛、补证请求、策略编辑、质量校验、人工审核 | 把有偏样本包装成总体洞察，或为凑篇数补写结论 |
| 工具与状态层 | 白名单接口、权限、预算、持久化、调用记录与故障处理 | 把外部文本当工具指令或自动重跑付费请求 |

LangGraph 继续只用于独立模块。目标流程：`brand_context → clarify → plan → confirm → collect → normalize → analyze → enrich_if_needed → edit → validate → human_review → export → feedback`。这是目标图，节点实现状态单独验收。

有限补证由明确的证据缺口触发，达到上限后降级为待研究或停止。确认计划与审核交付是不同暂停点。调用结果与执行账本独立于checkpoint，未知结果先核对，不盲目重试。

Editorial卡片按第7节的客户阅读规格呈现。内部处置采用select／research／observe／drop；历史action仅为兼容字段，后续实现须显式映射，不作为对客行动指令。代码只负责结构、权限、来源映射和质量约束；不能通过硬编码主题规则替代编辑判断。无合格结果允许零稿。

## 7. 精选交付契约：Selected Signals & Insights

### 7.1 产品止步于有用判断

周报优先以一封排版清晰的 HTML 邮件呈现：主题和开头直接给出鲜明判断，用短文配合支撑观点的数据或图表，关键口径就近简述，末尾集中列出 References 与原文链接。有可比数据才画图，不为展示效果编造数字；完整依据可链接展开。附件式 signal deck / brief 按需补充，不作为默认阅读入口。本轮先验证邮件样稿，尚未验收实际发送与邮件客户端兼容性。

内容从研究材料中选择值得带入品牌讨论的观察与理解，不做全面资讯汇编，也不自动生成策略方案。具体、直白不等于武断；审慎不等于只剩“加强关注、持续优化”等空话。

本轮撤回此前强制行动单中的负责人、截止日期和执行管理要求。产品可以指出一个值得核验的问题或可参考的表达角度，但不自动制定品牌定位、栏目排期、达人分工、预算增减、KPI目标或渠道方案。团队另行形成的策略可手动关联，不能由系统补写成已经决定的动作。

### 7.2 每期栏目与数量：先作为试点默认值

| 对客板块 | 数量与篇幅上限 | 入选条件 |
| --- | --- | --- |
| 本期精选 | 0—3条；每条一个独立判断 | 有可核查依据、明确新增理解或重要提醒，并与当前品牌问题有关 |
| 上期回看 | 0—1条；不超过120字 | 新证据实质支持、收窄或推翻旧判断；仅“仍在关注”不占版面 |
| 范围说明 | 一段，不超过100字 | 写明窗口、实际来源、覆盖缺口；不能用笼统全网字样 |

默认正文总量不超过1,000中文字符（含标题、回看及范围说明，不含来源名称、URL和展开证据）。设计目标为数分钟内读完，具体阅读时间需试点验证。月度摘要同样精选，不把四期周报串接；从全月候选中重新选择并交代变化。

数量是硬上限，不是配额；只有一条就交一条，没有合格发现则仅说明本期范围与结果。采集故障要明确列出，不能包装成“没有新信号”。内容／人群／达人／竞品／数据是内部研究维度和标签，不设必须填满的对客栏目。读者不需要看到每条研究路径的成果。

品牌交付设置保存栏目、数量、篇幅和读者用途，作为delivery_profile版本绑定到期次。员工可提出调整，审核人确认后生效；Agent不能因为材料多而自动扩版。本轮按上述默认值试两期，再依据阅读与编辑反馈校准。

### 7.3 一条卡片的表达规格

| 部分 | 建议上限 | 写法 |
| --- | --- | --- |
| 观点标题 | 26字 | 直接表达一个判断，避免仅写“养老趋势”“内容机会”；判断范围必须与证据一致 |
| 观察与理解 | 120字 | 用关键现象说明看到了什么，再说它补充或改变了什么理解；事实与推断不混写 |
| 对本品牌的参考 | 60字 | 指明与哪个已配置议题、沟通问题或理解盲点有关；不强行关联保险需求或行动 |
| 边界 | 45字 | 就近标明会改变理解的样本、时效或替代解释限制 |
| 可讨论的问题（可选） | 40字，最多1个 | 提出具体可核验的问题；没有必要就不写，不机械附“建议” |

每条正文合计不超过280字。界面不必把所有字段铺成五个小标题，保留自然短段落和层次。默认显示最关键的1—3个来源入口；完整证据、反例和编辑记录可展开，不按正文链接数截断实际证据链。来源不足不能伪造补齐，更多原始出处不得为压篇幅被删除。

字数检查负责发现不合格输出；超限交回编辑压缩、重写或删条，不能机器截断句子和限定语。来源不足或判断无价值，不能用漂亮标题掩盖。

### 7.4 信号、洞察与趋势的用词门槛

- **信号**：一个有意义的具体观察，可以来自单个案例，但必须说明个案边界；不靠出现次数自动升级。
- **洞察**：证据支持的理解进步，说明现象中的关系、约束、分化或意义；不要求惊人反转，也不因附了建议就成为洞察。
- **趋势**：需要可比较的时间序列、明确指标和覆盖口径，足以支持变化方向；单期热门、重复转载、搜索命中量不构成趋势。

这些是内部主张类型，不强制做成三个栏目。趋势证据不够时收窄为观察，不使用“正在成为”“越来越”等暗示时间变化的修辞。外部权威研究的趋势可转述，但需保留其对象与时期，不直接移植成品牌目标人群结论。

### 7.5 从多材料到少量判断的编辑选择

1. **材料去重与议题聚合**：保留不同原始来源和相反经验；相同观点换标题仍视为重复候选。
2. **候选解释**：围绕任务形成若干单一主张，分别关联证据、不同解释和新增理解。内部候选可多于最终交付，但受任务研究预算约束。
3. **门槛筛选**：必须通过来源可核查、主张有依据、任务相关、参考意义具体四项检查。未通过的转补证／观察／排除，不以高热度抵消缺陷。
4. **整期比较与精选**：比较谁更能增加读者理解，剔除泛泛常识、旧稿重复和低增量新闻；在最多3条中避免同义重复。不同维度有助于阅读，但不能为了均衡保留弱条目。
5. **定向补证**：只补会改变候选入选、措辞或边界的缺口；预算耗尽则收窄或不选，不继续无目的扩采。
6. **压缩与审稿**：先明确判断再精炼表达，保留证据限制。检查整期数量、篇幅、来源、越界建议与重复性；人工批准绑定具体版本。

每个候选保存select／research／observe／drop及简短理由；这些是内部编辑过程，不全部塞入客户稿。AI执行语义筛选和整期比较，代码校验数量、字数、来源ID与状态，不用机械热度榜、固定关键词或单一加权分取代主编判断。

### 7.6 表达边界示例（虚构，仅演示规格）

假设材料仅有若干关于笔记本使用体验的个案：

- 过浅：“用户体验值得关注，品牌应加强内容。”没有新增理解，也没有具体参考。
- 越界：“立即把30%预算转到便携主题，每周增加两条种草内容。”证据不能支持执行决策。
- 合适：“这些个案对笔记本的取舍，会随使用场景而变化。”正文交代个案事实与差异；品牌参考为“理解商品评价时，需要区分外出携带与固定场所使用”；可选问题为“已有评价是否区分不同使用场景？”不据此宣称人群趋势或商品策略已得到验证。

### 7.7 回看与读者反馈

反馈先记录“有参考／已知或重复／依据不足／无关／值得补证”，可附一句理由。采用为内容或策略素材由人主动记录，不设置系统自动派工或执行追踪。下一期只有新证据或实质理解变化才重新入选，不能反复推送相同话题。

验收至少覆盖：12个候选只选最强的最多3条；全部不合格时零条；同源转载不算趋势；强个案按信号呈现；重复议题不再次入选；超字数重写而非截断；有用但过度处方化的稿件被退回。两期业务试读检查读者能否说清关键判断、依据边界和参考用途，记录阅读负担、空泛率与越界建议数。设计门槛为交付零条无依据主张、零条越权执行指令；测试结果另行记录。

## 8. 服务方案与 Sun Life 应用

通用产品定义能力，品牌服务方案定义约定范围与额度，不能把 Sun Life 数量写成全产品固定规则。

Sun Life v11 当前提案口径：基础每月1次摘要、最多10条证据核验；可选升级每月4期周报与行动单（提案原称）。依本轮产品边界，建议将其对外说明收敛为“精选信号与讨论参考”，原提案与SOW需另行同步，不能静默认定已改。升级核验额度须与最终SOW对齐。v3报价保留“每期最多10条”与点点抽测旧文案，和v11去掉点点的方向不一致；这是待同步商务事项，不纳入本轮能力承诺。本次仅改PDD，未修改报价。

一条证据核验是对某份原始证据的出处、可访问原文、时间、适用范围及支持主张程度的检查记录；同一来源跨渠道不重复核验计数，重新核验记录原因与时间。无法核验须显示未完成，不能当作合格额度消耗。核验不等于证明作者个人叙述为真。

定价需覆盖人工研究与审稿、数据调用、模型成本和维护。试用或附赠要限定范围与周期；基础月报和升级不重复计费。尚无验证的成交价、效果或ROI不写入产品承诺。

产品介绍建议收敛为“信号—精选判断—讨论参考—回看”；Sun Life另作品牌应用，示例不冒充真实监测发现。真实试跑记录保持原来源、窗口和个案限制，不与概念案例混写。

## 11. 0.2.1：营销任务入口与开发语境隔离

日期：2026-10-07。本轮确认通用PDD定位基本成立，偏差主要在生活议题化的默认措辞、示例及用户入口。研究问题可以是策略层面的；交付判断须与证据强度相称，不能因不自动生成策略方案就把研究范围缩成生活内容选题。

### 开发、客户与运行三种边界

- 开发：`InsightBot-signal-desk` 独立工作树、`codex/signal-desk` 分支，通用模块、模板、PDD和测试均在该仓库。无需另建客户专属产品仓库。后续专门的产品任务应从此工作树开始，不默认导入客户提案对话。当前对话的既有上下文不能通过移动文件清除，因此须用显式规则与测试约束。
- 客户：Sun Life 提案和商业规格仍在客户目录，仅当试点任务明确需要时引用。它是一个应用品牌，不定义产品默认研究对象。
- 运行：品牌资料与任务继续按brand_id隔离；不迁移、删除或改写已有真实品牌数据。通用模板不预填客户名、教育金、退休、家庭照护等行业内容。

### 开始方式

进入品牌后直接在对话中描述营销问题或项目。七类营销任务用于助手组织方法，可提供中性示例，不要求用户先选择类型。必要时追问，用户可以回答或选择“暂不确定，你先建议”；说明建议采用的假设及下一步。检索词是计划产物，不要求用户先发明所谓议题。

“持续议题”对客改为“跟踪问题（可选）”，用于需要持续回看的研究，置于次级位置。独立研究不受其约束。方案建立和修改在同一连续对话内完成；刷新与再次打开任务恢复记录，切换品牌清空临时上下文。未回答追问时不自动开始研究，已有提案也须满足执行条件。对话能力不代表所有营销数据已经接入。

### 验收追加

- 七类营销任务均可生成合法、有限、需确认的研究计划；内容模板仍兼容既有任务。
- 品牌只填名称和行业，不能自动被引到该行业某个生活话题；需要用户明确营销问题或选择探索方向。
- 自由文本补充作为澄清语境，不整段当作关键词；显式检索词与历史对话分别处理。
- 用虚构文具、电器或服务品牌验证入口和提示，不用真实客户材料默认测试外部模型。
- 0.2既有品牌权限、审核、3条精选与篇幅上限保持回归通过。

## 12. 三栏研究工作区与自动执行

日期：2026-10-07。依据 Mika 对手动检阅、对话修改、节点流程及自动执行时间的要求追加。参考 [MiniMax Design 公开介绍](https://design.minimax.cn/) 中对话拆解、画布节点与关键审核的交互思路；具体研究方法和来源边界仍以本产品为准。

- 左栏按有权限的品牌分组，列出该品牌的具体任务，可搜索、折叠、切换及新建任务。任务名称可修改，自动执行时间与当前状态可见。
- 中栏为任务详情：节点流程与节点说明、手动方案设置、自动执行设置及历次执行记录。节点对应实际选用来源与执行状态；不是装饰图，也不让用户编辑内部协议。手机在任务详情与对话之间切换。
- 右栏为持续对话：提出问题、回答追问、调整方法与范围、提议执行时间。手动和对话修改更新同一任务与方案；日程提议及启用、暂停的操作反馈进入同一对话记录。

### 时间设置

本机先支持一次、每天、每周，按北京时间（Asia/Shanghai）显示具体时间与下次执行。观察范围可选择方案指定日期、最近7／30天、本月／上月、本周／上周。滚动日期在每轮实际执行时计算；比较窗口保持同样长度和先后关系。

用户可以说“每周一早上9点，看上周的讨论”，或直接修改时间表单。时间提议先保存和预览，点击“启用自动执行”后才生效；可以随时暂停。自然语言时间解析只支持明确的上述频率与时间，含糊或不支持的说明请用户在时间设置中补足，不静默猜测。

启用时绑定当前有效的研究方案、查询、来源和每轮额度。定时执行只滚动日期，不自行改研究方法、扩大范围、增加来源或额度，也不自动批准交付。方案或时间修改后暂停待重新确认；权限失效、未完成的方案修改、来源调用失败或结果不明会停止后续自动执行。已发出的请求无法撤回。

本机服务每30秒检查时间，服务运行时才执行。关闭、重启、明显休眠或错过的时间不补跑；已有研究仍在执行时跳过该次，避免重复调用。时间设置及执行记录持久保存，单次自动运行与原任务关联；这不是操作系统常驻调度或商用可用性承诺。

### 追加验收

品牌分组、节点点击、手动与对话修改同步、一次／每日／每周设置与暂停、刷新恢复、手机切换必须通过；后端覆盖冻结范围、日期滚动、并发去重、旧方案拒绝、撤权、失败暂停及重启不补跑。虚构数据测试与真实来源验收分别记录，不以自动触发演示替代真实研究质量及两期业务试读。当前实现与验证见 [本机记录](LOCAL-V02.md)。

## 13. 可管理研究工作流：Kestra 本机原型

日期：2026-10-07。Mika 同意先验证 Kestra 的本机原型，再决定正式产品迁移范围。现有 0.2.1 工作区继续运行；原型使用独立入口、虚构品牌及独立状态目录。启动和验收记录见 [LOCAL-V02.md](LOCAL-V02.md)。

方案中的节点、连接、模块设置和方案版本是共同依据：对话生成结构化修改，手动检阅修改同一份方案，画布按实际方案绘制，执行按该方案编译。拖动布局保持版本；修改研究问题、节点配置或连接关系递增版本，并暂停旧日程。已运行任务保留原方案与审核稿快照。

原型的模块包括品牌资料收集、竞品资料收集、竞品对照、研究整理、人工检阅与发布渠道。所有模块都有明确设置和输入输出；对话只能使用已开放的模块。画布支持拖动、连线及重接，保存前检查依赖、环路与审核路径。资料节点仅使用明确虚构的测试样本；工作台、企业微信、飞书均为模拟发布选项。

原型中，Kestra 负责节点依赖、一次／每日／每周调度、等待审阅及重启恢复；应用负责方案快照、受控模块、稿件版本和模拟发布账本。研究完成后必须等待人工选择；批准绑定当前执行的准确稿件，“不发布”跳过发布。结果不明的启动、模型调用或日程安装不能自动重发，也不能显示为成功。漏过的日程不补跑。正式接入时继续由应用承担品牌权限、凭据、额度与真实发布的管理，避免在应用和执行引擎之间维护两套自动调度。

本轮实际验证了已有模型连接下的竞品节点增加与分析重点修改、原生定时执行、人工暂停、服务与引擎重启后保留原执行、批准后单次模拟发布，以及不批准时不执行发布。实际采集、专业编辑及真实频道尚未接入本原型，不能将虚构样本验收等同于研究质量验收。

正式迁移前继续解决：将千瓜等来源及现有精选编辑接成模块；保留每品牌权限、凭据和额度边界；逐个确认模块版本与接口；校验真实频道的审批、幂等和失败处理。管理员维护来源、方法和发布模块目录属于下一阶段；普通用户通过对话、节点设置和时间卡片完成配置。现阶段保留受控模块目录，尚未开放任意代码和无限制流程搭建。

## 14. 0.2.2：数据源分工按实现基准改写

日期：2026-10-12。本轮依据 2026-10-11 起的实测证据，正式改写 §1 决策条与 §5 来源表中 JustOneAPI 的定位，并澄清千瓜的能力边界。**改写的原因是初版表述与实现基准冲突**——初版把 JustOneAPI 移出核心依赖，而实测确认笔记正文与评论原文只有它取得到。

- **不在本轮范围内**：§7 交付契约、§9 实现顺序与验收、品牌分区与权限边界均不变。本次是**来源定位的改写，不是范围扩张**；只重写与数据源定位直接相关的表述，其余正文保持原样。
