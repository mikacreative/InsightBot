> **v0.2.10 修订记录（2026-10-12 产品形态裁定：全自动 + 契约式把关）**
> **① 产品形态已定：全自动执行，人在"批准关口"把关一次。** 人把关的不是"某条证据对不对"，而是一份**契约**——这个任务是否在【一定预算范围、执行方式、交付标准】内自动化执行。批准后**全自动**，证据守卫全部强制、**无人 override**。**新增 §4.2。**
> **② 保留三类升级（escalation）**：**费控预警**、**无产出预警**、**提供选择**（主要选项＝换模式）。**"提供选择"不是锦上添花**：全自动下没有人在场接住零稿，系统必须能自己说明"为什么 + 下一步可以选什么"，否则产品会**在客户面前安静地失败**（§4.2）。
> **③ 前置的是"预测"，不是守卫。** 一个自然的推论是"判断全部前移到批准关口"——**半对**：守卫**不能搬**（准入规则需要真实证据才能执行，批准时还没有证据），能前移的只有**"守卫会不会被触发"的预测**。本版为此确立新的待设计组件——**执行前契约体检（pre-flight）**：预计花费、预计层覆盖、零稿风险。**系统今天没有任何预测能力**（`budget` 是上限、`collection.summary_only` 是事后计数）；设计稿见 `PREFLIGHT-DESIGN-v0.1.md`。
> **④ 千瓜采购口径定性（关闭 §9.2 第 4 项）**：千瓜是**既有资源**（qiangua-insights 项目另有用途），**其席位／档位不由本项目决定**。本项目对千瓜的角色是**消费者 + 证据提供方**——产出**能力依赖清单**（硬依赖／已证明可替代／未解），作为**未来是否续订、以及续订时必须保住哪些基础要求**的参考证据。**"采购重议"不是本项目的待办，而是本产品产出的一份证据。**
> **⑤ §9.2 第 15 项（模式-任务不匹配）随形态裁定落定**：批准关口上升为**契约不合格项**、定时配置关口**硬拒**、执行关口保持提示——因为全自动下**没有人在事后接住零稿**。
> 受影响章节：**新增 §4.2**；更新 §9.2（4 关闭并定性、15 关闭）、文末证据声明；新增文档 `PREFLIGHT-DESIGN-v0.1.md`。

> **v0.2.9 修订记录（2026-10-12 千瓜结构层与时间轴接通）**
> **① L3／T 两层从"零实现"变为可达。** 新增 `research_v2.STRUCTURE_READS`（读取注册表）＋ `survey()`（一轮的定位读取），接千瓜 `brand.get_sov_chart`（品牌 SOV 趋势）、`brand.get_blogger_pyramid`（合作达人金字塔）、`keyword.note_trends`（检索词日序列）。**七类任务里 品牌与竞争（缺 L3）与 数据与变化（缺 T）的常驻缺口随之消失**，剩余缺口只有 L2（人群与使用情境、达人方向）与 L4（产品与价值理解）。
> **② 结构化读取不走费控，这是刻意的。** 费控门禁防的是**按次计费**的供应商被超支（JustOneAPI ¥0.15／次）；千瓜**按席位计费**，一次结构读取**不花任何变动费用**，只消耗席位月度额度。因此额度是一个**调用次数**而非金额，计划照旧冻结它。把这类读取送进门禁会更糟：它会报出**从未发生的花费**，并让一个**已经付过钱的席位**看起来买不起。
> **③ 聚合证据的出处规则已定（关闭 §9.2 第 8 项）。** 笔记类证据靠**页面 URL** 可追溯，聚合证据没有页面——它的出处是**供应商＋能力名＋时间窗**。`editorial_v2` 现在按等级分流：`grades.is_note_text()` 为真的仍必须带合法 URL，为假的必须带完整出处描述符（`vendor`／`capability`／`window` 两项俱全），**未知等级一律按笔记类处理**（fail-closed）。渲染同理：无页面来源渲染为出处描述，而不是一个空链接。§9.2 第 8 项推荐的"② 千瓜证据只用于结构层／趋势层"由此**落到代码**。
> **④ 类目级读取（`category.funnel`／`category.trends`／`category.overview`）不接，缺口如实记账。** 三者接受 `tag_id` 参数，但对 `tag.list` 能列出的所有标签 id，上游返回 `500 品类传参有误` 或全零载荷 → **类目 id 的来源仍未解开**。按猜测接线正是"把零当成测量结果"的开端，故列为 §9.2 第 16 项。

## 1. 出发点：小红书为什么能支撑决策

不理解平台机制，方法论就是工具罗列。小红书有三重特殊性，各自对应一类决策价值：

### 1.1 决策前置场 → 暴露决策卡点

用户在**做消费决策之前**来小红书"做功课"。因此内容反映的不是"兴趣"，而是**决策过程中的问题、比较与犹豫**。

- 决策价值：不是"多少人讨论"，而&#x662F;**"卡在哪一步"**——犹豫点、比较维度、未被回答的疑问
- 这是社媒数据对**商业决策**最有价值的部分：问卷问不出"用户自己还没意识到的卡点"，但笔记和提问会自然暴露
- 方法含义：研究设计要**主动采集"问题型内容"**（提问、求推荐、对比、避坑），不能只采高互动内容

### 1.2 语言原生 → 提供可复用语料

用户表达未受问卷污染。品牌拿到的不是"洞察报告"，而是**可以直接用的词**。

- 决策价值：文案词汇、搜索占位词、卖点表述顺序
- 方法含义：语言采集要**保留原话与上下文**，不做同义归并（归并会丢掉最有用的差异）
- **v0.2.1 修正**：正文**可达，但须按需取**（§5）——搜索层只给 ≤60 字符摘要，语言采集的粒度应升级为"**正文原话（终选阶段取 detail）＋话题标签＋评论区自述**"，三层语言各有用途（表达／归类／异议）。**不要指望检索阶段批量落正文**：截断摘要会把"表达"层降级成"归类"层。

### 1.3 结构可测 → 支持定位判断

**部分供应商**提供 SOV、达人金字塔、类目漏斗、榜单等**结构化指标**，这类数据不是"看几条笔记"，而是**对照**。

- 决策价值：竞争位置、投放结构差异、品类营销化程度
- 方法含义：结构层能力**不可由内容层推导**——采一万条笔记也推不出 SOV
- **v0.2 更正**：结构化能力**只有千瓜提供**，JustOneAPI 不提供。因此"结构可测"这一特殊性**绑定特定的数据源**，不是小红书平台的普遍属性

## 2. 证据阶梯：四层 + 一条时间轴

同一份社媒数据，能支撑的决策强度完全不同。分层是为了**让判断强度与证据强度对齐**（PDD §4.2 要求）。

| 层          | 回答的问题     | 能力示例                             | 主要决策用途         | 证据强度     | **主源**            |
| ---------- | --------- | -------------------------------- | -------------- | -------- | ----------------- |
| **L1 内容层** | 用户在说什么    | 笔记搜索、笔记详情、**评论全文**、热搜、话题、关键词联想   | 内容方向、表达素材、话题切入 | 观察／样本    | 千瓜／**JustOneAPI** |
| **L2 人群层** | 谁在说、谁在看   | 达人搜索与详情、粉丝画像、粉丝增长趋势、标签体系         | 人群假设、达人选择依据    | 样本推断     | 千瓜＋**JustOneAPI** |
| **L3 结构层** | 谁占多少、怎么分布 | 品牌 SOV（趋势／排名）、达人金字塔、类目漏斗、发布分布、榜单 | 竞争定位、投放结构诊断、时机 | **对照比较** | **千瓜（独占）**        |
| **L4 商业层** | 卖什么、卖得怎样  | 商品搜索、商品销量榜、店铺榜、直播销售、跨平台商品与评价     | 品类机会、产品验证、渠道判断 | 平台口径     | 千瓜＋JustOneAPI     |
| **T 时间轴**  | 在往哪走      | 关键词／品牌／类目趋势、节日关键词、达人粉丝趋势、同口径重采样  | 趋势判断、节奏规划      | 时间序列     | **千瓜（独占）**        |

### 2.1 三条使用规则

1. **越往上，越要靠对照，越不靠单点。** L1 可以凭一条笔记成立（个案），L3／L4 必须同窗同口径比较（PDD §4.2）。
2. **L3／L4 是决策含量的来源。** L1 回答"做什么内容"，L3 回答"我在什么位置、该往哪打"，L4 回答"这个品类值不值得进"。原产品链路只覆盖 L1，所以只能产出内容级建议。
3. **T 是唯一能支撑"趋势"这个词的来源**（PDD §7.4）。L1 的重复出现、热搜命中量，都不构成趋势。

### 2.2 补充：L1 内部也有强弱

v0.2 新增。同为 L1，证据价值差别很大：

| L1 子层   | 内容                                           | 决策用途                           |
| ------- | -------------------------------------------- | ------------------------------ |
| **正文层** | 笔记 `desc` 全文（**须经 `get-note-detail/v1｜v6`**） | 表达素材、内容结构、卖点叙述顺序、**可直接复用的语言**  |
| **摘要层** | 搜索结果 `desc`（**≤60 字符，被截断**）                  | 议题归类、话题标签归因——**不可用于语言复用**      |
| **标题层** | 标题、话题标签                                      | 议题归类、搜索占位词                     |
| **评论层** | 评论全文与楼中楼                                     | 异议、复购线索、未被回答的问题、**决策卡点的最直接暴露** |
| **指标层** | 点赞／收藏／评论／分享                                  | 内容获得分发的程度（**不得推断需求**）          |

> 方法含义：**正文层与评论层是 L1 的价值所在，指标层最弱但最容易被误读**。v0.1 因接口限制只能拿到标题层＋片段层；v0.2 起，正文层与评论层应作为 L1 默认采集目标。  
> ⚠️ **v0.2.1 补充**：**"摘要层"与"正文层"必须分开记等级**。搜索接口的 `desc`（≤60 字符）足以支撑归类，但不足以支撑"卖点是怎么说的"——把截断摘要当正文引用，是这一版最容易犯的方法论错误。

### 2.3 结构性缺口（不变）

原产品链路**只接了两条内容样本链路**（且检索接错线），L3 结构层能力**在代码里一个都没接**。这是最大的落地缺口——L3／L4 是决策含量的来源，却完全缺席。

### 2.4 供应商分层（v0.2 新增）

| 供应商            | 定位           | 独占能力                                                                                  | 成本形态                                          |
| -------------- | ------------ | ------------------------------------------------------------------------------------- | --------------------------------------------- |
| **千瓜**         | 结构／对照层供应商    | 品牌 SOV、达人金字塔、类目漏斗、各类榜单、平台级趋势序列                                                        | 固定（席位年费 + 月度额度）                               |
| **JustOneAPI** | 原文／人群／跨平台供应商 | **笔记完整正文（经 `get-note-detail`，非搜索）**、评论原文、蒲公英投放数据（报价／性价比／内容广场）、**跨 34 平台**采集、纯 API／MCP | 变动（按成功调用计费：搜索 ¥0.15—0.20／次、正文 ¥0.15／条；余额不过期） |

**架构含义**：方法论必须**按供应商声明能力**，而不是假设"所有能力都来自同一家"。详见 `DATA-SOURCES-v0.1.md` §3 的能力互换性判断。

> **v0.2.3 单价更正**：正文单价由"≤¥0.10／条"更正为 **¥0.15／条**（与检索 v2 同价）；`get-note-comment/v2` 亦为 **¥0.15**。此前误判源于**计费异步结算**（单笔延迟入账，差值恰好伪装成"免费"）——**单价必须以官方价目表为准，余额只用于对账**。详见 `JUSTONEAPI-ASSETS.md` §2.6／§2.8 A。
>
> **同样重要的是能力面的确证**：官方文档与实测共同确认，**两个供应商的搜索接口都只能给摘要**——JustOneAPI 搜索 `desc` 截断至 60 字符；千瓜 `note.search_by_url` 实测 40 字段无任何内容字段。**正文层的唯一入口是 JustOneAPI `get-note-detail/v1｜v6`。**

| 层             | 文档声明能力                                                     | 代码事实（2026-10-11 核对）                                                                                              | 判定     |
| ------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------ |

**三条由此确认的结构事实**：

1. **证据等级词汇表与"层"词汇表不是同一维度。** `grades.py` 的八个等级中，`note_meta`／`note_segment`／`note_comment`／`note_body` 与 §2.2 的 L1 四个子层一一对应；`note_structure`／`note_linked` 是笔记级属性而非层；`brand_structure` 与 `trend_series` 分别对应 L3 与 T。**L2 与 L4 在等级体系里没有位置**——这是待补的设计缺口，不是疏漏。
2. **任务声明与其层需求已显式化（v0.2.4）。** `research_v2.METHODS[*].layers` 按 §3.8 声明每类任务所需的层（primary／aux）；`IMPLEMENTED_LAYERS` 登记管线实际可达的层；`layer_gaps()` 报告两者之差。**任务声称某层而管线达不到时，缺口会写进计划与运行结果的 limitations**，不再依赖人工比对。这正是本次核对里"靠 grep 才发现"的那个问题，现在成了可程序化检查的失败。
3. **核对当日的缺口读数（v0.2.4；括号内为 v0.2.6 补入第 7 类后的读数）**：**七类**任务中**五类**存在 primary 层缺口——**品牌与竞争缺 L3、产品与价值理解缺 L4、人群与使用情境缺 L2、达人方向缺 L2（新增）、数据与变化缺 T**；平台与渠道、内容与沟通的 primary 层（L1）可达。这与 §3.8"2 类必须依赖千瓜"互为印证：那两类正是缺口最深的两类。
4. **缺口读数已随 L3／T 接通收窄（v0.2.9）**：**七类中只剩三类带常驻缺口**——产品与价值理解缺 L4、人群与使用情境缺 L2、达人方向缺 L2。品牌与竞争与数据与变化**不再带缺口**（这正是 §9.2 第 4 项"千瓜采购口径重议"现在才有数据可依的原因）。**另一种缺口措辞不变**：模式不采集某层仍写 `未覆盖`（换模式可解），与管线没有读取器的 `未接入`（补读取器才可解）分开说——`人群与使用情境 × 速读` 是**两头都缺**的实例，两行同时出现，互不顶替（§9.2 第 15 项）。
5. **结构性读取的额度不是钱（v0.2.9）**：`structure_reads` 是一个**调用次数**，由模式自己的层声明派生（`mode_structure_reads()` ← `MODES[*].layers`），因此**默认模式 `probe` 的派生值为 0**——"不点名模式＝行为不变"这条不变量由构造保证，不是特例判断。计划可以把它调**低**（读取列表随之截断，意图与上限不会互相矛盾），但不走进费控门禁（理由见文首修订记录 ②）。

> ⚠️ **本轮最重要的落地后果**：在正文通路接通前，v2 链路是**千瓜单源**，而千瓜最高只到 `note_segment`（`summary_only=True`）——守卫会**正确拒掉全部摘要级材料**，管线因此**产不出任何可交付卡片**。这不是守卫过严，而是"摘要不等于正文"这条纪律把**接错源**暴露了出来：映射做对了，缺口就藏不住了。接通 `get-note-detail` 是恢复产出的唯一路径，已在本版落地。

## 3. 决策问题 → 证据配方（双源版）

PDD §4.1 已定七类决策任务。每类配**证据层、能力链（主源／备源）、额度成本、输出形态、禁止推论**。

### 3.1 内容方向

| 项    | 内容                                                                                                                   |

## 4. 三种研究模式与节奏

额度约束下，方法必须**先声明模式，再决定采集规模**。三种模式对应三种决策强度与三种节奏。

| 模式           | 触发           | 证据层         | 调用量     | 节奏    | 产出                  |
| ------------ | ------------ | ----------- | ------- | ----- | ------------------- |
| **速读 Scan**  | "最近这个议题什么情况" | L1 + T      | 2—3 次   | 周度    | 议题地图：在用的词、内容模式、明显空白 |
| **定向 Probe** | "这个判断站得住吗"   | L1（含评论）+ L2 | 5—10 次  | 事件驱动  | 带证据的观察 + 边界 + 待验证问题 |
| **结构 Frame** | "我们在什么位置"    | L3 + L4 + T | 10—20 次 | 月度／季度 | 竞争与品类定位观察           |

**设计意图**：把"要采多少"从"素材够不够"改成"判断需要多强"。这直接回应 PDD §5「数量是上限不是最低产量」——**额度不是产量目标，是模式决定的成本**。

**模式与交付的关系**：周报以 Scan／Probe 为主（0—3 条精选），Frame 产出沉淀为品牌工作区的结构基线，供后续各期引用，不必每期重跑。

**v0.2 补充**：三种模式的**供应商落点**不同——Scan／Probe 以 JustOneAPI 为主（变动成本，低频不浪费），Frame 触发千瓜调用（固定成本，只用在不可替代处）。这让固定成本只发生在真正需要结构层的时候。

> **v0.2.7 裁定：节奏是建议值，不是日历。** 产品在用户端按需自定义工作流（可 agent 辅助修改），节点式逻辑保持——因此上表"节奏"列（周度／事件驱动／月度季度）只是**默认建议**，实际节奏由用户的工作流与定时决定。模式冻结与派生额度的是**判断强度**（证据层与调用配额），不是"多久跑一次"。代码里 `MODES[*].cadence` 由此改为建议值语义。

### 4.1 模式落进执行层（v0.2.6）

上面这张表在 v0.2.5 之前**只活在费控层**：`costcontrol.RECIPE_CALLS` 有模式的调用量，可以被 `quote_recipe()` 报价，而 `research_v2` 里**没有模式概念**——所有计划共用一套 `BUDGET_DEFAULTS`，于是**Scan 与 Frame 只差价格，不差额度**（一根 12 次正文的探针，可以被报成 ¥0.55 的 Scan）。本版把模式变成执行层的概念。

| 模式 | 证据层（§4） | 一轮的调用配额 | 上限 | 节奏 | 产出 |
| --- | --- | --- | --- | --- | --- |
| `scan` 速读 | L1 + T | 检索 ×2 ＋ 正文 ×1 | **¥0.55** | 周度 | 议题地图 |
| `probe` 定向 | L1 + L2 | 检索 ×2 ＋ 正文 ×3 | **¥0.85** | 事件驱动 | 带证据的观察与边界 |
| `frame` 结构 | L3 + L4 + T | 检索 ×3 ＋ 正文 ×6 | **¥1.50** | 月度／季度 | 竞争与品类定位观察 |

**落地方式（三件事）**：

1. **额度由配方派生，不另写一套。** `research_v2.mode_budget(mode)` 从 `costcontrol.RECIPE_ALLOWANCES` 取 `queries` 与 `body_reads`，其余额度（样本、模型调用、背景条目）保持 `BUDGET_DEFAULTS`——§4 只说调用量与证据层，其余数字**没有出处就不另设**。因此"报出的价格"与"允许的调用"共用同一个数字，分叉在结构上不可能。
2. **默认模式 = `probe`，其派生额度恰好等于 `BUDGET_DEFAULTS`。** 这是"不点名模式就不改变行为"的机械保证（由 `tests/signal_desk/test_modes.py` 锁定），也是为什么模式上线**不带回归风险**。
3. **计划冻结额度，执行不重算。** 模式随计划冻结（与 §6.4 的四项冻结同理：**大小会变的量不是可比量**）。执行层读的是**冻结的额度**，不是 `mode` 这个标签——否则某天有人改了 `MODES`，一份批准过的 Scan 会**自己长大**成 Probe。模式只在一处被重读：**完全没有额度**的计划，用它做播种。

> ⚠️ **照配方核对时发现的两处不一致（本版修正其一）**
>
> | 发现 | 依据 | 处置 |
> | --- | --- | --- |
> | **Scan 只配了 1 次检索** | §3 要求每个计划**至少一条挑战查询**（＋一条定向查询）→ 单查询的 Scan **连计划都过不了**（`planning_errors`） | 配方改为 **检索 ×2** |
> | **Scan 不取正文** | §4 说 Scan 产出"**在用的词**"，而 §2.2 明令 ≤60 字符摘要**不可用于语言复用** → 只检索的 Scan **产不出它声称的产出** | 配方改为 **正文 ×1**（＋¥0.15／期） |
>
> **两处都指向同一件事**：配方（成本）与产出（承诺）此前从**未互相核对**过。核对后 Scan 由 ¥0.20 变为 **¥0.55**；Probe／Frame 经核对**无需改动**，这反过来说明原先的偏差只出现在"最便宜的那一档"——**最便宜的一档最容易被当成"不需要成本"而免于核对**。

**两种缺口必须分开说。** 一个任务可以因为**管线**够不到某层而弱（§2.5：L2／L3／L4／T 无读取器），也可以因为**模式**不采该层而弱（一个 Scan 回答品牌竞争问题）。**处置完全不同**：前者要补读取器，后者要换更大的模式。因此代码里是两条不同的判据、两种不同的措辞：

| 判据 | 含义 | 措辞 |
| --- | --- | --- |
| `missing_primary_layers(task)` | 管线**没有**该层的读取器 | `本轮未接入 … 证据层` |
| `mode_shortfall(mode, task)` | **这一模式**不采集该层 | `本轮为…模式，未覆盖…` |

两者都写进计划**与运行结果**的 limitations（UI 渲染 `collection.limitations`，只写计划是看不见的）。**不阻断**：用速读回答品牌竞争问题是**故意要一个更弱的读数**（§6.5 降级链），不是非法计划——但"更弱"必须写在纸上。

**花费按模式可分离。** 一个信封覆盖同一品牌同一期的**所有**模式，所以每笔预留都带上 `mode`；`costcontrol.report()` 因此提供 `by_mode`／`spent_by_mode`。没有这个标记，"Frame 的真实成本是否为 ¥1.50"这个问题在账本上**无法被回答**——而这正是配方存在的前提。

### 4.2 人在环路中的位置：契约式把关（v0.2.10）

**产品形态裁定（2026-10-12）：目标形态是全自动。** 人**不在执行链上**，只在**批准关口**把关一次——把关的对象不是"某条证据对不对"，而是一份**契约**：这个任务是否在【一定预算范围、执行方式、交付标准】内自动化执行。

| 契约要素 | 含义 | 系统里已有的载体 |
| --- | --- | --- |
| **预算范围** | 这一期最多花多少 | `Envelope`（`SIGNAL_DESK_SPEND_LIMIT_CNY`），期界＝`Asia/Shanghai` 自然月 |
| **执行方式** | 用哪个模式、允许多少调用 | 冻结的 `mode` + 派生额度（§4.1） |
| **交付标准** | 出几条、多少字、来源必须可核查 | `delivery_profile` + §5.3 的两条强制约束 |

批准即授权：此后采集、定位、编辑**全自动**，证据守卫全部强制、**无人 override**。三要素**都已经有载体**——本版要补的不是新概念，而是把三者**显式聚合为一份可签署的契约**（"这三样合起来就是本次授权的边界"）。

**三类升级（escalation）**：全自动不等于"无人可问"。三类情况必须升级给人——

| 通道 | 触发 | 现状（代码） | 设计状态 |
| --- | --- | --- | --- |
| **费控预警** | 预计花费将超信封，或消耗比例越过阈值 | `costcontrol.report()` 已有 `by_mode`／`spent_by_mode`，缺阈值触发 | 设计已定（§4.2 末） |
| **无产出预警** | 本轮预计／实际无法产出任何卡片 | **无**。原料＝层缺口（§2.5）＋ `summary_only` 计数（但那是**事后**的） | **⚠️ 现状是"静默零稿"**——已裁定改为**调度暂停 + 升级**（§4.2 末） |
| **提供选择** | 升级时必须附可选动作 | **无**。主要选项＝**换模式**（唯一改变判断强度的动作），并列加额度、收窄议题、换任务类型 | 已裁定并入 pre-flight 体检 |

> **⚠️ 为什么"提供选择"是前提而不是补充。** 全自动下**没有人在场接住零稿**。守卫拒了稿、系统却只会报一句"零稿"，产品就会**在客户面前安静地失败**。所以"无产出预警 + 提供选择"不是体验优化，是全自动能够成立的**必要条件**。

**⚠️ 前置的是"预测"，不是"守卫"。** 既然判断要尽量前置，一个自然的推论是"把守卫搬到规划关口"。**这半对**——能前移的只有**"守卫会不会被触发"的预判**，守卫本身**不能搬**：准入规则（§5.2／§5.3）需要**真实证据**才能执行，而批准时还没有证据。

| 能前移（预测） | 不能前移（只能在执行后判定） |
| --- | --- |
| 预计花费（配方 × 额度，确定） | 支持证据是否**全部**为摘要层 → 触发守卫 |
| 预计层覆盖（`missing_primary_layers` / `mode_shortfall`，确定） | 正文数字是否真的出现在支持原文里 |
| 交付规格是否可满足（`delivery_profile`，确定） | 编辑六项质检是否通过 |

**这暴露了一个现状：系统今天没有任何预测能力。** `plan` 里的 `budget` 是**上限**不是预测；`collection.summary_only` 是**事后**计数；`limitations` 是警示语、且 UI 并不渲染它（`renderPlan()` 只出 6 行摘要）。全自动 + 判断前置要成立，必须补一个**执行前契约体检（pre-flight）**组件——预计花费、预计层覆盖、零稿风险。设计稿见 `PREFLIGHT-DESIGN-v0.1.md`。

**模式与任务的匹配随形态裁定落定**（关闭 §9.2 第 15 项）。此前 `mode_shortfall()` 只是 limitations 里的一行且**不阻断**（理由：用速读回答品牌竞争问题是"故意要一个更弱的读数"）。全自动下这个理由不再成立，因为**没有人在事后接住零稿**：

| 关口 | 全自动下的行为 |
| --- | --- |
| **批准关口**（人工签契约） | `mode_shortfall` 上升为**契约不合格项**：必须处理——换模式，或**显式接受**一个更弱的交付标准。不再只是"写一行 limitations" |
| **定时配置**（无人签契约） | **硬拒保存**。没有人能签这份契约，就不该存在这份契约 |
| **执行中** | 保持提示，**不阻断**。方案已批准，且 §6.4 要求执行层忠实于冻结额度 |

**千瓜的定位不在本产品的授权范围内**（关闭 §9.2 第 4 项）：千瓜是**既有资源**（qiangua-insights 项目另有用途），其席位／档位**不由本项目决定**。本项目对它的角色是**消费者 + 证据提供方**——产出**能力依赖清单**（硬依赖／已证明可替代／未解），作为**未来是否续订、以及续订时必须保住哪些基础要求**的参考证据（§6.2）。

**前置的是预测，落地它的是一个组件（pre-flight 契约体检）。** §4.2 上一段说明"能前移的只有预判"，本段把这件事的**形态裁定**落定（2026-10-12，设计稿 `PREFLIGHT-DESIGN-v0.1.md`）。三条已裁定，两条保留：

| # | 议题 | 裁定 |
| --- | --- | --- |
| 1 | **结构性零稿的处理** | **fail-closed**：零稿**不得**落成干净的 `awaiting_review`，须标独立终态（`empty_delivery`）并**暂停该定时计划 + 升级**。理由：全自动下无人接住零稿，调度继续跑＝**在客户面前安静地失败**，这直接动摇全自动的前提 |
| 2 | **断言阈值与硬拒关口** | **只在 `H == 0` 断言零稿；`H > 0` 仅提示。** 定时配置关口对 `H == 0` **硬拒保存**（与 §9.2 第 15 项的分关口处理同构）；批准关口**只警告不阻断** |
| 3 | **Envelope 是否冻结进计划** | **采纳"批准即承诺、之后可审计"**：信封**快照进计划**，**执行读快照**而非现读 `env`。⚠️ 代价是**门禁行为有一处可见变更**（批准后被改的环境变量不再影响该次执行）——换来的是"契约的两个时刻真正是同一个数" |
| 4 | 零稿风险：先二元还是给概率 | **未裁定**（保留）。概率需先埋点采集正文可得率与摘要占比，当前**无真实比率** |
| 5 | `preflight` 是否参与 `plan_hash` | **未裁定**（保留）。写进计划会让 hash 变化 → 旧 collection 缓存失效；两条路＝排除出 hash，或作旁挂派生字段 |

> **辨析（重要）**：`H`（非摘要证据可达上界）是**能力上界**，不是实际产出预期——它把"不会兑现的能力"也算进去了，因此**系统性低估零稿风险**（偏乐观）。所以"确定"级只敢放在 `H == 0` 这一支；`H > 0` 不做任何"不会零稿"的承诺。**这不是保守，是诚实**——与 §5.2「未知等级按更严规则处理」同一条纪律。

> **⚠️ 现状与本设计的差距（必须说清）**：以上 1—3 只是**裁定**，`PREFLIGHT-DESIGN-v0.1.md` 是**设计稿，代码一行未动**。**今天系统仍存在静默零稿**：零稿通过校验、状态落 `awaiting_review`、定时任务不暂停（`workspace_v2.py:884`）——即"这一期什么都没产出来，系统不告警、不停机"。**在全自动目标下，这是必须先补的洞，而不是可选优化。**

### 5.3 两条强制约束（v0.2 新增）

**① 来源随证据落库。** 每条证据必须带 `source` 字段（`qiangua` / `justoneapi` / `manual`）。理由：双源之后，同样的"笔记样本"来自不同采集口径，混在一起无法复核，也无法在供应商故障时判断哪些证据受影响。

**② 不许跨源拼接同一等级。** 例如 `trend_series` 只能来自千瓜（唯一提供平台级序列的源）；若用 JustOneAPI 定期重采样自建序列，必须标为 `trend_series_sampled` 并声明采样口径——它支持的方向性判断强度**低于**平台原生序列。


### 5.4 对 `_note()` 的影响

现行 `_note()` 要求 URL 合法才保留，真实链路上导致 `kept=0`（检索接错线）或恒为 `title_only`。v0.2 后的目标行为：

- 检索切到正确能力后，`note_body` **仅对终选笔记**取 detail 落正文（JustOneAPI 路径，**N+1**）；搜索结果只落 `note_segment`／`note_meta`
- 千瓜路径下正文仍不可得，**必须显式标注 `note_meta`**，而不是沿用"降级为 `title_only`"的统一表述——两种来源的证据强度不同，不应共用同一个降级口径
- **URL 不应再作为保留门槛**：实测搜索返回的 `url` 字段恒为空，但 `explore/<id>` 裸 URL 实测 HTTP 200 可访问 → `source_id` → URL 的构造应无条件成立，`kept=0` 不应再出现

## 6. 额度预算与降级（v0.2 修订）

### 6.1 能力纳入设计的门槛（新增）

一个能力要进**证据配方（主路径）**，必须通过额度门槛检验：

```
可支撑品牌数 = 月额度 ÷ (单品牌单期调用量 × 每月期次)
```

人工量级下，单品牌月用量约 **30—50 次**（取 40 为基准）。分档结论：

| 档     | 月额度     | 可支撑品牌数 | 处置                          |
| ----- | ------- | ------ | --------------------------- |
| **宽** | ≥2400   | ≥60    | **主路径**：可作配方的默认能力           |
| **中** | 200—900 | 5—22   | **按预算使用**：期次规划时须声明，不得作为常规步骤 |
| **窄** | **≤50** | **<2** | **不进设计**：不作为任何配方的必需能力       |

### 6.2 千瓜侧分档与排除清单

| 能力                | 月额度    | 档         | 处置                       |

| 笔记分析 / 跳转原文       | 4500   | 宽         | 主路径                      |
| 笔记搜索              | 4000   | 宽         | 主路径（**注：正文不可得，仅得元数据**）   |
| 达人搜索              | 2400   | 宽         | 主路径                      |
| 关键词搜索             | 800    | 中         | 按预算                      |

| 笔记内容解析            | 20     | 窄         | **排除**                   |
| **评论搜索**          | **15** | **窄**     | **排除**（改由 JustOneAPI 承担） |

### 6.3 JustOneAPI 侧（按次计费）

- 计费单位：**每次成功调用**（`code=0`）；失败不计费；余额不过期
- 单品牌年用量估算 ≈ **600 次**（Scan 8／月 + Probe 16／月 + Frame 25／月）
- 单价**已于 2026-10-11 由官方价目表确证**（⚠️ 修正 v0.2.2 的推测值）：`search-note/v2` ¥0.15 ／ `search-note/v4` **¥0.20**（现用）／ `get-note-detail/v1｜v6` **¥0.15** ／ `get-note-comment/v2` **¥0.15**
- **计费规则（官方确证）**：**只有 `code=0` 计费**；`100／301／302／303／400／500／600／601／602` 全部不计费。已转录为 `costcontrol.BILLING_CODES`
- 按"每期 1—2 页检索 + 3 条正文"：1.5 × ¥0.20 + 3 × ¥0.15 = **≈¥0.85／期**（修正前 ¥0.70）→ 24 期／年 → **单品牌年成本 ≈ ¥20**
- **单条完整研究链上限**（`costcontrol` 已验证）：`scan` **¥0.55** ／ `probe` ¥0.85 ／ `frame` ¥1.50
  > **v0.2.6 更正**：`scan` 原记 **¥0.20**（1 次检索），是按"速读只检索"设的。照 §3（须有挑战查询）与 §2.2（摘要不可复用为语言）核对后，配方改为 **2 次检索 + 1 条正文 = ¥0.55**——原配方**既过不了计划校验、也产不出 §4 承诺的"在用的词"**。详见 §4.1。
- ⚠️ **"全量取正文"的代价被低估过**：一页 17 条全取正文 = 0.20 + 17 × 0.15 = **¥2.75／页**，是纯检索（¥0.20）的 **13.75 倍**。这就是"正文必须后置于终选"的量化理由
- 与千瓜的关键差异：**无月度归零压力**，额度不因"这个月没跑"而损失

### 6.6 费控／额度中台（v0.2.3 新增）

额度纪律如果只写在文档里，落地一定失败——**必须进代码**。因此把价目表从"参考文档"升级为产品能力，三层结构：

| 层 | 实现 | 职责 |
| --- | --- | --- |
| ① 报价 | `pricing.py` | 版本化价目表快照（296 端点 × 35 平台）；端点命名归一；`quote()`／`cheapest()` |
| ② 门禁 | `costcontrol.py` | **品牌 × 期信封**（`Envelope`）；`authorize()` 预授权；**未知单价／未开通端点一律拒付** |
| ③ 账本 | `costcontrol.py` | 追加式 JSONL（`0o600`）；`reserve` → `settle` 两阶段；`reconcile()` 与账户余额对账 |

**四条设计要点**：

1. **fail-closed（报价方向）**：查不到单价的端点**不是"按 0 算"，而是拒绝**。宁可挡住一次可用调用，不可放行一次不可控支出。
2. **fail-closed（计费码方向，方向相反）**：遇到未知业务码**视为已计费**。两个方向都指向同一目标——**绝不悄悄少算钱**。未知码多算的成本会在 `reconcile()` 里以 variance 暴露，少算则永远不会被发现。
3. **pre-call reserve 防双花**：MCP（OAuth）与 REST（env token）**共享同一余额池**——这是 §2.4 双源架构带来的真实风险。官方文档补上了第二个理由：**同一条通路的重试**（官方建议 120s 超时的原因正是"避免网络抖动导致重复请求"）。授权时先写 `reserve` 行，因此重试／并行／跨通路都不会对同一余额重复授权。
4. **本地账本只是估算**：§6.3 已证计费**异步结算**，因此账本数值不等于账单。`reconcile()` 用余额差分纠正，差额写回而非静默吞掉。

**配方成本上限**（即 §6.1「能力纳入设计的门槛」在代码里的落地形式）：

| 配方 | 调用构成 | 上限 | 一轮的额度（v0.2.6 起） |
| --- | --- | --- | --- |
| `scan` | `search-note/v4` ×2 ＋ `get-note-detail/v1` ×1 | **¥0.55** | 检索 2／正文 1 |
| `probe` | `search-note/v4` ×2 ＋ `get-note-detail/v1` ×3 | **¥0.85** | 检索 2／正文 3 |
| `frame` | `search-note/v4` ×3 ＋ `get-note-detail/v1` ×6 | **¥1.50** | 检索 3／正文 6 |

> **v0.2.6：这张表同时是价格与额度。** 在此之前它只是价格——`quote_recipe()` 能报价，却不能约束任何一次运行（所有计划共用一套 `BUDGET_DEFAULTS`）。现在 `research_v2.mode_budget()` 从**同一张表**派生额度，两者的关系从"两张表应当一致"变成"一个数字的两种读法"（§4.1）。

> **与 §6.1 门槛规则的关系**：§6.1 约束的是**千瓜侧**（月额度 ÷ 单品牌单期调用量 → 可支撑品牌数）。JustOneAPI 侧没有月度归零，约束对象是**可变现成本**，因此改用"配方信封"：每期开一个信封，超出即拒付。两者是同一纪律在不同计费形态下的两种写法。
>
> **第二配额轴：已决（2026-10-12，§9.2 第 9 项）**：官方确证存在"用户 × 接口"的**每日成功请求限额**（`Asia/Shanghai` 自然日、**跨所有 TOKEN 合并计数**、超限 `303`+429 不计费）。`Envelope` 目前只建模货币，方案**可能通过金额校验、却在调用时被上游拒掉**——纳入费控已获批，**待实施**（新开工项；期界与货币轴不同：次数按自然日、金额按自然月）。机制细节见 `JUSTONEAPI-ASSETS.md` §2.9 C。

#### 6.6.1 接线（v0.2.5 完成：门禁已强制，不再是"建好但没人走"）

v0.2.3 建成三层后，`costcontrol` 处于**"建好但没有调用点"**的状态——**花钱的路开着，门禁却不在路上**。v0.2.5 把唯一付费调用点（`research_v2.enrich` 的正文补读）逐次接入：

| 环节 | 行为 |
| --- | --- |
| 选读取器 | 有 token **且**声明了信封 → JustOneAPI；缺任一项 → 免费片段读取器，并把原因写进 `collection.limitations` |
| 调用之前 | `require({get-note-detail/v1: 1}, 品牌 × 期信封)` → **先写 `reserve` 行** |
| 调用之后 | `settle(reservation_id, code=<业务码>)` → `code=0` 计费，其余按 ¥0 结算 |
| 命中缓存 | **不预留、不结算**——缓存命中不是调用，为它记账就是凭空收费 |
| 额度不足 | 本轮停止，后续目标标 `budget_denied`，并写入 `collection.errors` |

**信封来自环境变量，不来自默认值**：`SIGNAL_DESK_SPEND_LIMIT_CNY`（账本位置可选 `SIGNAL_DESK_SPEND_LEDGER`）。**未声明即不花钱**——"没写下来的上限不是上限"。这与 §2.2 的 fail-closed 同构：**看不清就不花钱**。注意这条**独立于 token**：有 token 不等于有花钱许可，这正是"能买"与"被允许买"必须分开的原因。

**顺带修正一条账本语义：结算释放预留。** 此前 `remaining` 只减 `reserve` 行，于是一次失败调用会**永久占住**额度——一个月的失败足以把信封耗空而实际零支出，即**一个会自己关闭的门禁**。现在 `consumed` ＝ 已结算的实际值 ＋ 仍未结算的预留估算值：未结算的预留照样占用（防双花不减弱），结算后按其实际值计，因此**失败调用按 ¥0 结算即等于退还**。`reconcile()` 仍用 `reserved()`（估算值）与账单对照——两者回答的是不同问题，故保留两个函数而不是合并。

**业务码必须由读取器带出来。** `settle(code=...)` 只有在能拿到业务码时才有意义；靠解析错误文案取码"能用，直到文案被改写"。因此 `providers.ProviderError` 显式携带 `code` / `http_status`，失败调用据此按码结算，而不是按预留额多记。

**v0.2.6：每笔预留带 `mode`。** 信封是「品牌 × 期」，**同一期内三种模式共用一个上限**；不带模式标记，账本就无法回答"那次 Frame 实际花了多少"，而 §4.1 的配方（¥1.50）恰恰是要拿真实成本去对照的。`report()` 因此新增 `by_mode` 与 `spent_by_mode`，并可按模式过滤金额（`mode=`）——**上限仍是信封的，不被模式切分**，只有花费按模式分离。


### 6.4 可复现性要求（趋势的前提）

趋势判断需要"每期等量、同口径"。研究计划必须冻结四项并在每期滚动时保持不变：

**关键词集 × 时间窗长度 × 样本上限 × 排序方式**

方案版本（`plan_version`）变化即暂停自动执行（PDD §12 已有此约束）。与额度的关系：**额度决定样本上限的可行值，一旦定下就不得因"这期素材多"而上调**。

> v0.2 注意：改用 JustOneAPI 后，"样本上限"的约束对象变为**调用次数与翻页深度**（实测每页 17—20 条），冻结项应表述为「每次调用页数上限」而非"条数"。

### 6.5 降级链（双源版）

```
主源能力不可用／额度耗尽
  → 备源同层替代（标注来源与口径变化）
  → 降级为观察（不出判断，只记现象）
  → 本期零条（PDD §7.2「全部不合格时零条」）
```

**额度应作为调度器的输入而非运行时撞墙**：

- 千瓜侧：建议增加 `user.quota` 只读能力（读 `User/GetUserOperationCountV3?type=N`）
- JustOneAPI 侧：调用前查余额与每日限额，`303`／`601` 视为降级信号而非错误

## 7. 边界与禁止推论

不写这一节，方法论一定会被用越界。以下每条都对应一次真实的过度推断风险：

| 数据                | 容易被推断成    | 实际只能支撑                    |
| ----------------- | --------- | ------------------------- |
| 互动量高              | 需求大／用户认可  | 内容获得了分发；点赞是算法行为           |
| 笔记样本分布            | 总体占比      | 样本内分布（PDD §4.2）           |
| SOV 排名            | 市场份额／销量   | 声量份额                      |
| 类目漏斗的品牌／商业／广告占比   | 投放 ROI    | 品类内容结构                    |
| 商品销量榜             | 全渠道销量     | 平台内交易排名                   |
| 粉丝画像              | 购买意愿／财富水平 | 兴趣与人口结构倾向                 |
| 时间序列的短期波动         | 趋势        | 需覆盖口径与指标明确的持续方向（PDD §7.4） |
| 平台内出现某内容          | 品牌应照做     | 值得核验的观察                   |
| **蒲公英报价／性价比（新增）** | 投放效果预期    | 平台标价与历史表现参考               |
| **达人粉丝增长（新增）**    | 该达人值得投    | 账号处于增长还是停滞（不含转化信息）        |
| **跨平台内容（新增）**     | 全渠道声量     | 各平台各自口径的观察，**平台间不可直接加总**  |

**一条总则**：社媒数据支持**观察、比较、定位与假设**；不支持**因果、ROI、销量预测与执行指令**（PDD §7.1 已划定产品不自动给投放方案）。

### 8.2 正文通路与层声明落地（v0.2.4，2026-10-11）

#### A. 接通 `get-note-detail`：唯一能到 `note_body` 的路

`research_v2.enrich()` 原先只有一个读取器（千瓜 `note.search_by_url`），因此**整条 v2 链路没有任何一条证据能达到 `note_body`**。新增 `providers.JustOneApiAdapter`（与 `QianguaAdapter` 同接口：`configured`／`auth`／`search`／`detail`），在 `enrich` 阶段优先读取正文。

| 决定                                       | 理由                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| **检索仍走千瓜，正文走 JustOneAPI**                | 千瓜是固定成本席位，花掉它的额度正是付费的原因；而正文的唯一来源是 JustOneAPI。**这是声明式的分工，不是失败回退**        |
| **无 token／未声明信封时退回千瓜片段**                  | 更弱证据、不额外花钱；无 token 时行为与接通前**逐字节一致** → 接通本身不带回归风险                             |
| **读取器进缓存键**（`enrich-detail-<reader>-<hash>`） | 否则"先无 token 跑过、后补 token 重跑"会命中旧缓存，**静默拿不到正文**                            |
| **`body_reads` 跨读取器合并计数**（`BODY_OPERATIONS`） | 换读取器不能买到额外读取额度                                                           |

**实测确认的响应形状**（这是本次最不可省的一步）：

```
get-note-detail/v1  →  data 是 list，正文在 data[0].note_list[0]（61 字段）
search-note/v4      →  data.notes[]（元素直接是 note）
```

**两个端点形状不同**，写死任一侧都会静默出错。因此读取器**对任何非预期形状直接报错**（`detail_note()`），绝不猜测——猜测的代价就是把 60 字符摘要当成正文归档。

> **成本含义**：该响应约 **80k 字符**，而其中的笔记正文只有几百字符（本次实测 108 字符，且该笔记正文本身只有话题标签）。**正文是"重载荷、小文本产出"**，这从成本侧再次印证 §6.3：正文只对终选取，不对整页取。
>
> **顺带修掉一处静默风险**：`justone_note_detail()` 原先只从环境变量读 token，而适配器的 `token` 参数形同虚设——两者不一致时，会在很久之后以一句无关的"未配置"报错。现由 `_auth_token()` 统一解析，注入值与环境不可能各说各话。

#### B. 任务的层需求变成可检查的声明

`research_v2` 新增三件东西：

- `LAYERS` = `('L1','L2','L3','L4','T')`，配 `LAYER_PRIMARY`／`LAYER_AUX`
- `METHODS[*].layers` —— 按 §3.8 声明每类决策任务所需的层
- `IMPLEMENTED_LAYERS` + `layer_gaps()` —— 登记管线实际可达的层，并**报告两者之差**

缺口会同时写进**计划**与**运行结果的 limitations**，UI 直接可见。**这让"任务名声称 L3、采集只有 L1"从"必须人工 grep 才能发现"变成"可程序化检查的失败"。**

当日读数（**v0.2.6 补入第 7 类后更新**）：**七类**任务中**五类**存在 primary 层缺口——品牌与竞争缺 L3、产品与价值理解缺 L4、人群与使用情境缺 L2、**达人方向缺 L2**、数据与变化缺 T；平台与渠道、内容与沟通的 primary 层（L1）可达。

> **v0.2.6 补充：这是"管线"一侧的缺口。** 另一侧——**模式**够不够（如速读覆盖不到 L3）——是**另一条判据**，措辞也不同（`未覆盖`），理由与两表见 §4.1。两条判据合起来才回答"这一轮为什么弱"。

#### C. 付费读取接入门禁（v0.2.5）

A 接通后留下一个不对称：**花钱的路开了，门禁却不在路上**——`costcontrol.require()` 从未被调用，授权实际只靠"是否配了 token"。v0.2.5 把它接上，并暴露出三处**只在真正接线时才显形**的问题：

| 发现 | 后果 | 处理 |
| --- | --- | --- |
| **结算不释放预留** | 一次失败调用**永久占住**额度 → 一个月的失败把信封耗空而实际零支出（**会自己关闭的门禁**） | 新增 `consumed()`＝已结算实际值 ＋ 未结算预留估算值；`remaining` 改用它 |
| **业务码藏在错误文案里** | `settle(code=...)` 拿不到码 → 失败调用只能按预留额多记 | 新增 `providers.ProviderError`，显式携带 `code`／`http_status` |
| **缓存命中也会被预留** | 为一次**没有发生的调用**记账 = 凭空收费 | 预留前先判缓存；缓存命中不预留、不结算 |

不变量仍然保持：**未结算的预留照旧占用额度**（防双花不减弱），只有**结算后**才按其实际值计。`reconcile()` 保留用估算值对照账单——两个函数回答的是不同问题，因此不合并。

**信封只从环境变量来**（`SIGNAL_DESK_SPEND_LIMIT_CNY`）。这不是省事，而是把"这个部署允不允许花钱"变成**部署决策**：默认值会让任何一个调用方在忘了传参数时拿到花钱的许可，而忘了传参数恰恰是最常见的情形。未声明时的行为是**安全降级**（免费片段 ＋ 明写 limitation），不是报错。

> **一条仍在外面的路**：MCP 侧（本机直调 `call_endpoint`）不走本账本，只能靠"同一个信封"的人工约定。**门禁保护的是管线，不是账户**——§9.2 第 11 项已记此遗留。
